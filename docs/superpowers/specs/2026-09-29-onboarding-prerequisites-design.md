# Предварительный этап onboarding до Hatchet

## Цель

Подготовить работающий HTTP-сценарий регистрации, выпуска инвайта и заполнения профиля в двух NestJS-сервисах и общем Next.js-интерфейсе. На этом этапе Hatchet, worker-процессы и публикация событий не реализуются.

Цель этапа — проверить модели данных, публичные HTTP-контракты и UI независимо от оркестрации. Когда будет добавлен Hatchet, интерфейсы браузера не меняются: worker Person вызовет уже существующий внутренний endpoint выпуска ссылки, а обработчик заполнения профиля заменит временное прямое сохранение на событие и durable task.

## Границы

Входит в этап:

- регистрация пользователя в Person;
- выпуск и проверка одноразовой ссылки в Profile;
- сохранение профиля напрямую в Profile;
- страницы `/person`, `/invite` и `/profile/[token]` в `apps/web`;
- API-клиенты, тесты контроллеров/сервисов и миграции Prisma.

Не входит в этап:

- SDK Hatchet, workflow, workers, runId и polling статуса run;
- отправка email;
- аутентификация, JWT и защита внутреннего API общим секретом;
- длительное ожидание события и retry-логика.

## Модели данных

`Person` остаётся владельцем учётных данных. `ProfileLink` хранится в базе Profile: токен, `personId`, срок действия и время использования. `Info` должен содержать `personId` с уникальным ограничением, чтобы один пользователь мог завершить профиль только один раз.

`ProfileLink.personId` также уникален. Повторный запрос выпуска ссылки для того же пользователя возвращает действующую неиспользованную ссылку; после истечения или использования создаётся новая ссылка. Токен — криптографически случайная строка, срок действия — 24 часа.

## HTTP-контракты

### Person API (`:3001/api/v1`)

- `POST /register` принимает `{ email, password }`, хеширует пароль внутри Person и возвращает `{ personId, email }` с `201`.
- `GET /persons/:id` возвращает `{ id, email, isProfileCompleted, createdAt }`; хеш пароля наружу не выдаётся.
- `PATCH /persons/:id/profile-completed` — внутренний подготовительный endpoint. Помечает пользователя завершившим профиль. В текущем этапе его вызывает Profile API после сохранения данных; в этапе Hatchet его будет вызывать задача `mark-profile-completed`.

Ошибки валидации отдаются как `400`, дублирующий email — как `409`, отсутствующий пользователь — как `404`.

### Profile API (`:3002/api/v1`)

- `POST /internal/links` принимает `{ personId }`, создаёт или возвращает действующий `ProfileLink`, отдаёт `{ token, profileUrl, expiresAt }` с `201`. Эндпоинт оставлен внутренним по семантике: пока он запускается вручную из Swagger/curl, позднее его вызовет worker Person.
- `GET /profiles/:token` проверяет токен. При успехе возвращает `{ personId, expiresAt }` и `200`; истёкший или уже использованный токен — `410`; неизвестный — `404`.
- `POST /profiles/:token` принимает `{ firstName, lastName, personalStatement }`, повторно проверяет токен, сохраняет `Info` c `personId`, помечает ссылку использованной и вызывает Person `PATCH /persons/:id/profile-completed`. При успехе возвращает `{ profileId, personId }` и `201`.

Если вызов Person API после записи профиля не удался, endpoint отвечает `502`. Компенсирующая логика и ретраи появятся вместе с Hatchet; в этом этапе такая ошибка видна и воспроизводима для обучения.

## Web-сценарий

1. `/person`: форма email/пароль вызывает `POST Person /register`, показывает `personId` и направляет пользователя на `/invite?personId=...`.
2. `/invite`: по `personId` объясняет, что выпуск ссылки пока запускается внутренним API вручную. Пользователь вставляет полученный URL или токен; страница направляет на `/profile/[token]`.
3. `/profile/[token]`: перед показом формы вызывает `GET Profile /profiles/:token`; при `410` выводит понятное сообщение. После `POST Profile /profiles/:token` показывает подтверждение, что профиль сохранён.

Каждый API-клиент находится в `apps/web/app/api/` и преобразует неуспешный ответ в отображаемую ошибку. Компоненты не знают адресов сервисов напрямую.

## Тестирование

- Person: регистрация хеширует пароль, не выдаёт хеш, отклоняет дублирующий email.
- Profile: ссылка создаётся идемпотентно, просроченный/использованный токен даёт `410`, профиль сохраняется с `personId` и однократно отмечает Person как completed.
- Web: страницы показывают форму, ссылку и состояния ошибки; API-клиенты проверяются с подменённым `fetch`.

Полный end-to-end запуск с Hatchet не является критерием этого этапа. Проверяются unit/integration тесты сервисов и lint/build web-приложения.

## Переход к Hatchet

На следующем этапе `POST /register` будет стартовать run и вернёт `runId`; появится endpoint статуса регистрации. Выпуск ссылки переместится из ручного запуска в задачу `issue-onboarding-link`. `POST /profiles/:token` будет публиковать событие, а durable task сохранит `Info` и отметит Person. Публичный URL профиля, его payload и модель `ProfileLink` сохраняются без изменений.
